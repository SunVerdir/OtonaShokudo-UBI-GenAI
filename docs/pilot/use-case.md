# Pilot Use Case — 活動記録から月次報告・広報下書きへ

> **文書版：Draft 1.0（GENIAC応募・現場実証の設計たたき台）｜更新日：2026-09-26**  
> **状態：提案中。利用組織、実データ、現場導入、業務効果はいずれも未確認・未実証。**

## 1. ユースケース要約

| 項目 | 内容 |
|---|---|
| 仮称 | 食支援・地域活動の記録作成支援 |
| 対象ユーザー | 地域の食支援・生活支援の業務を実際に行う国内の団体・自治体等（組織名と応募資格は未確定） |
| 想定利用者 | 記録・報告・広報を担う職員または担当者（役割・人数は現場ヒアリングで確定） |
| 対象業務 | 活動記録の整理、月次報告の下書き、活動案内文の下書き |
| AIの役割 | 非機微な記録の要約、指定欄への構造化、原文に基づく下書き |
| 人間の役割 | 原記録との照合、訂正、内容確定、公開・提出の承認 |
| 実証範囲 | 合成データによる机上試験から開始。現場試行は組織合意・安全確認後に別途判断 |
| 給付・資格判断 | 対象外。UBI支給、利用資格、相談の緊急度等は判定しない |

本案は実際の現場組織が参加・承認した実証計画ではありません。GENIAC-PRIZEへの応募では、実際にAIを使うユーザー組織が主体となる要件を確認し、開発者と役割を分担します。

## 2. 現状と課題仮説

活動実施後に、担当者が自由記述、集計、月次報告、次回案内等を別々に作成している場合、情報の再入力や文章の整形に時間がかかる可能性があります。担当者が変わると表現・記録粒度が異なり、引継ぎや集計の負担になることも考えられます。

これらは**現場で確認すべき課題仮説**で、現時点で本プロジェクトが計測・確認した事実ではありません。実証開始前に、ユーザー組織の担当者と業務を観察・ヒアリングし、現行の工程、月当たり件数、所要時間、品質上の困りごとを記録します。

## 3. 対象業務と対象外業務

### 対象とする支援

- 活動メモの要約案を作る。
- 予め決めた項目（活動日、活動種別、提供食数、集計値等）の候補を抽出する。
- 入力にない情報は補わず、「記載なし」「要確認」とする。
- 月次報告や告知文の下書きを作る。
- 元データと生成物を並べ、担当者が照合・修正できるようにする。

### 初期版では対象外

- UBIその他の給付、支援、サービス利用資格の判定。
- 利用者の困窮度、健康状態、心理状態、緊急性の推定。
- 相談内容の診断、助言、支援の優先順位付け。
- 自動送信・自動公開・行政帳票の自動提出・自動確定。
- 実名、連絡先、生年月日、詳細な相談内容、生体情報を使ったモデル入力。
- 会計、現金、寄付、在庫、配食の実データを伴う「モノ・カネ二重監査」。

これらが将来必要になった場合は、個別にリスク・法令・責任主体・利用者への説明を再検討し、別の承認を得て設計します。

## 4. 想定ワークフロー

```text
1. 担当者が活動記録を作成（当初は合成データ／非個人情報のみ）
        ↓
2. 入力をAI処理用に確認・不要項目を除外
        ↓
3. 選定済みモデルが要約・項目抽出・文案を生成
        ↓
4. 担当者が原記録と照合し、訂正・却下・承認
        ↓
5. 承認済み文書だけを通常の業務手順で提出・公開
        ↓
6. 所要時間、修正、誤り、確認結果を最小限記録
```

AI案は未承認の下書きとして識別し、承認前に外部送信しません。AIを使わない従来工程へ戻す手順も用意します。

## 5. 現行プロトタイプと追加開発の境界

2026年9月26日に公開リポジトリの`app.py`を確認した範囲では、UBIの概念シミュレーターと固定条件分岐による「仮想大人食堂」のモック応答が実装されています。シミュレーターの係数は仮置きと明記され、チャット画面の文面は外部LLM呼び出しではありません。`index.html`は`app.py`をstliteで読み込む構成です。

したがって、本書で提案する活動記録の要約・帳票下書き機能、GIPUモデル接続、監査ログ、現場実証は、**確認済みの現行機能ではなく追加設計・実装案**です。現行デモの表示や仮のシミュレーション値は、現場での支援実績・制度効果・実測値を示しません。

## 6. ユーザー・開発体制とGENIAC準備

GENIAC-PRIZEテーマ1は、実際に業務でAIを使うユーザーが課題設定・実証・評価を担うことを求めています。応募主体は、次の項目を満たす組織・団体等を現場確認のうえ特定します。

| 役割 | 想定責任 | 現在の状態 |
|---|---|---|
| ユーザー組織 | 現場業務、業務課題、ベースライン、実証環境、現場評価、利用責任 | 未確定。組織名・応募資格・参加意思の確認が必要 |
| 開発担当 | アプリ、モデル接続、アクセス・ログ設計、テスト、技術資料 | 計画案。開発体制・役割・保守責任を確定する必要 |
| モデル提供者 | 正式モデル情報、利用条件、技術仕様、可能な範囲の技術連絡 | GIPUモデルを候補評価中。協業・支援契約は未確認 |
| 現場責任者 | 手順承認、AI出力レビュー、事故時の停止・報告 | 未確定 |
| 評価担当 | KPI定義、測定、分析、限界と失敗例の報告 | 未確定 |

応募前に、ユーザー組織を主体とする体制が成立しない場合は、開発者の構想だけで現場実証があるように表現しません。外部組織の名称・ロゴ・協力関係は、明示的な同意と事実確認なしに掲載しません。

## 7. 実証の段階

### Phase A — 机上設計

ユーザー候補へのヒアリング、対象業務の図示、合成データ作成、リスク整理、KPI定義。現場データは取得しない。

### Phase B — 合成データによるモデル比較

同一タスク・同一入力で候補モデルを比較する。正確性、欠落、根拠のない追加、人の修正時間、実行環境を記録する。安全ゲートを通過しない場合は、画面上のデモにとどめる。

### Phase C — 監督付きシャドー試行（条件付き）

ユーザー組織の承認、データ取扱い・安全管理、担当者研修、停止・事故対応を確定した場合に限り、AI案を通常業務に使わず並行生成する。実利用者への回答・公開は従来工程のままとする。

### Phase D — 限定実利用（別途承認）

シャドー試行の安全性と有用性が確認され、利用者組織が承認した場合に限り、担当者がすべての案を確認する範囲で限定利用を検討する。対象範囲を明記し、撤回・停止可能にする。

各フェーズへの移行は自動ではありません。評価結果、安全事象、現場負担、利用者への影響を踏まえ、ユーザー組織が進行可否を決めます。

## 8. 安全・プライバシー・人間の判断

- 初期開発では合成データを使用し、個人情報や機微情報を公開Issue・ソースコード・通常ログに含めない。
- 仮名化IDを用いる場合も、再識別可能性を評価し、鍵・対応表をモデル入力や公開ログから分離する。
- 出力には「AI下書き・未確認」表示を付ける。
- 給付・資格、緊急度、診断等の相談内容に対する判断を自動生成・自動実行しない。
- 担当者は元記録と照合し、承認・修正・却下できる。承認前に外部送信しない。
- 誤り、情報漏えい、差別的・不適切な出力の疑いがあれば利用を停止し、責任者に報告する。
- モデル、プロンプト、評価用例、依存ソフトの版を記録し、変更時は再テストする。
- 現場実証に移る場合は、データ管理者、目的、法的根拠・同意手続、保存期間、委託先、削除・訂正、事故対応を文書化する。

## 9. 成功・中止の判断

成功は「AIの回答が自然」だけでは判断しません。対象業務の所要時間、記録品質、人の修正負担、担当者が取り戻せた対人支援時間、記録の再現性、現場が継続可能な負荷をKPI計画に沿って評価します。

次の場合は拡大せず、停止・再設計します。

- 重大な捏造、支援資格の誤判断、実データの漏えい・無断保存が発生した。
- 人の確認負担が増える、又は対象業務の正確性が低下する。
- 現場が説明・訂正・停止できない。
- ユーザー組織、法的・倫理的条件、保守体制が確保されない。
- 国産基盤モデルの要件・利用条件に未解決の重大な不確実性が残る。
