# AI Model Selection — OtonaShokudo-UBI-GenAI

> **文書版：Draft 1.0（応募・実証計画のたたき台）｜更新日：2026-09-26**  
> **状態：候補評価中。モデル採用、GENIAC要件適合、現場実証は未確定。**

## 1. 目的と結論の要約

本書は、地域の食支援・生活支援業務を補助するプロトタイプに用いるモデル候補と、選定・検証の手順を定めます。現段階の提案は次のとおりです。

- **初期PoCの第一候補：GIPUのUD Japanese iMatrixシリーズから、Qwen3.5-4B UD-japanese-imatrixの実際に入手可能な版を検討。** 主な用途は、テスト記録の要約と項目別の下書き生成です。
- **比較候補：** 同シリーズのGemma 4 E2BまたはE4B等から1モデルを選び、同じテストケースで比較します。モデル名、正確なリビジョン、量子化ファイルを確定後に記録します。
- **GENIAC-PRIZE要件：** 事業者名だけ、ブランド名だけ、あるいはGGUF量子化であることだけでは適合確認になりません。公式リストの該当行、モデルの名称・版・開発者・基盤モデルとの関係、募集要項上の定義を照合し、確認できるまで「適合済み」と記載しません。
- **採用判断：** 実機での品質・速度・メモリ・運用性評価とライセンス確認を経て行います。候補を実証に使う前に、実利用者組織とユースケースも確定します。

ここで挙げるモデルは評価候補であり、特定モデルの採用、GENIAC応募要件の充足、GIPUとの協業契約を示すものではありません。

## 2. 対象ユースケース

対象は、現場職員・支援者が作成した**機微情報を含まないテスト用活動記録**から、活動日報・月次報告の下書きを作るタスクです。

想定するAI機能：

1. 非個人データの自由記述を短く要約する。
2. 日付、活動種別、人数等の指定項目を抽出する（未記載は推測せず「不明」とする）。
3. 公開用の活動案内文の下書きを作る。
4. 入力にない事実や給付・支援資格の判断を作らない。

**初期評価では実利用者の個人情報、相談記録、生体情報、自由記述の機微データを入力しません。** 実証段階へ進む場合は、データの必要性・法的根拠・利用目的・同意または適切な手続・保存・処理環境を利用組織と確認します。

## 3. GENIAC-PRIZE要件とモデルの適合性確認

GENIAC-PRIZEテーマ1の公式案内では、応募は実際の利用者（ユーザー）が主体であること、開発・実証において国産基盤モデルの利用が必要であることが示されています。募集要項は国産基盤モデルの開発者・モデルの登録と定義に関する条件を置いています。量子化や実行形式だけでは、基盤モデルとしての開発条件を満たすとは限りません。

### 提出・実証前の必須チェック

| チェック | 確認するもの | 完了条件 |
|---|---|---|
| 事業者 | テーマ1公式ページと掲載Excel | 応募時点の現行リストで事業者を確認し、参照日とファイル版を保存 |
| 正式モデル | 登録されたモデル名と、実証で使うファイル名・版 | ブランドやシリーズ名ではなく、実際に使うモデルを一意に特定 |
| 開発関係 | 開発主体、基盤モデル、事前追加学習・ファインチューニング等の関係 | 公式定義との関係を開発者情報・モデルカード等で説明可能 |
| 技術仕様 | モデル版、量子化方式、GGUFファイル、実行ランタイム | Hugging Face等のモデルカード、配布元、SHA-256、設定値を記録 |
| 要件判断 | 募集要項・FAQ・必要に応じ事務局確認 | 未解決点があれば適合と断定せず、確認先と回答を記録 |
| 利用権 | 対象の個別モデル・派生物のライセンス | 商用・再配布・改変・データ利用条件を当該版について確認 |

2026年9月26日時点で、公式テーマ1ページはGIPUを国産基盤モデル開発事業者の一つとして掲載し、公式リストのダウンロード先を案内しています。GIPUの公開カタログはUD Japanese iMatrixのGGUFモデルとして、Gemma 4／Qwen3.5ベースのモデル等を案内しています。**ただし、事業者が掲載されていることは、そのシリーズ中のすべての量子化ファイルが個別に要件適合することを自動的に意味しません。** 提出時点の公式リスト上の具体的なモデル表記と、募集要項上のモデル定義を必ず照合します。

## 4. 候補モデルと選定理由

| 候補 | 用途の想定 | 現時点の判断 | 追加確認 |
|---|---|---|---|
| Qwen3.5-4B UD-japanese-imatrix（GIPUカタログ表記） | 日本語の活動記録要約、項目抽出、公開文案の下書き | **第一候補。** 軽量なローカルPoC候補として同一タスクで評価 | 提出時点の公式登録モデルとの同一性、ファイル版、ライセンス、手元端末での性能 |
| gemma-4-E2B-it UD-japanese-imatrix | 小メモリ環境との比較、短い定型タスク | 比較候補 | 実効サイズ・実メモリ・ライセンス・品質を当該版で確認 |
| gemma-4-E4B-it UD-japanese-imatrix | 品質と必要計算資源の比較 | 比較候補 | モデル版、評価用量子化ファイル、ライセンス、端末要件を確認 |

製品カタログ掲載名はモデル候補を発見するための手掛かりです。実験計画書・応募書類には、ダウンロード元に記載された正式なリポジトリ名、ファイル名、リビジョン、量子化表記、ライセンスを転記します。

## 5. 評価計画

### 5.1 テストセット

- まず**合成・架空データ30〜50件**を作成し、入力文と期待する出力項目を人が定義します。件数は初期スクリーニング用であり、統計的な一般化や現場効果の証明には使いません。
- ケースは、正常記録、必要項目の欠落、曖昧な表現、否定・訂正、日付や人数の不一致、根拠のない質問を含めます。
- 入力にない事実を補ってはならない試験、未記載を「不明」とする試験、支援資格や給付の判断を拒否して担当者へ回す試験を含めます。
- 各ケースの期待値と重大度をモデル出力を見る前に定義します。実データを使う場合は、利用組織の承認を得た上で匿名化等の適切性を評価し、合成データで代替可能かを先に検討します。

### 5.2 比較方法

1. 同一の入力、指示、出力形式、ランタイム条件で各モデルを実行する。
2. 各出力を、モデル名を伏せた状態で人が確認できる場合はブラインド評価する。
3. 事実誤り、重要な欠落、根拠のない追加、指示不遵守、文章修正量を記録する。
4. 実行時間、ピークメモリ、CPU/GPU、電力・費用を可能な範囲で同一条件で測る。
5. 各候補の成功例だけでなく、失敗例、再現手順、制約を保存する。

### 5.3 品質評価軸

- **事実忠実性：** 入力と一致し、入力にない事実を作らない。
- **項目抽出：** 必須欄の正答、未記載欄の適切な空欄・不明表示。
- **安全な境界：** 給付・支援の可否を推定せず、人の確認へ誘導する。
- **人の修正負担：** 承認までの確認時間、修正箇所、全面書き直し率。
- **運用性：** 応答時間、必要メモリ、起動安定性、実行環境の再現性。
- **利用条件：** ライセンス、モデル更新、依存ソフトウェア、問い合わせ・保守方法。

## 6. 初期の採用ゲート（提案値）

以下は現場ユーザー・評価担当者との合意前の**暫定ゲート案**です。実証の閾値は、業務リスクとベースラインを確認した後に事前登録します。

- 全出力が人の承認前に利用者向け・行政向け確定記録として扱われないこと。
- 合成テストセットで、重大な捏造・誤認識・不適切な給付判断が1件でも出た場合は、原因分析と対策が完了するまで現場試行を開始しない。
- 第一候補の中央値処理時間または人の総作業時間が比較対象より悪化しないこと。**20%削減は検討用の仮目標**であり、現場ベースラインを見て設定を確定する。
- 出力ごとにモデルID・バージョン・入力ケースID・生成時刻・人の確認結果を再現可能な形で記録できること（入力に実個人情報を含めない初期試験）。
- GENIAC提出を行う場合、該当モデル・事業者の適合性確認と利用権確認が完了していること。

これらは性能保証や現場成果ではなく、試行へ進むための提案条件です。

## 7. 実行環境と記録

実測前に端末構成は未確定です。評価ログには次を記録します。

- OS、CPU、RAM、GPU（型番・VRAM）、ストレージ、ランタイムと版
- モデル配布元、正式名、ファイル名、リビジョン、量子化方式、SHA-256
- プロンプト／テンプレート版、パラメータ、コンテキスト長、実行時設定
- テストケースID、実行日時、生成時間、ピークメモリ、出力、評価、修正
- 失敗・再実行・手動介入・評価者と判定基準

本番・現場実証では、誰がモデルを管理し、更新を承認し、脆弱性・障害に対処するかを利用組織と決めます。ローカル実行を採用しても、端末アクセス制御、バックアップ、ログ保全、データ削除等の安全管理を別途行います。

## 8. 意思決定と再評価

**現在の決定：** Qwen3.5-4B UD-japanese-imatrixを初期PoCの比較開始候補とする。これは条件付きの技術候補であり、GENIAC要件適合・最終採用を意味しない。

次の条件を満たした時点で選定結果を記録します。

1. 利用者組織と具体的な業務を確定。
2. 正式な配布版・モデルカード・ライセンスを固定。
3. 最新公式リストとの照合とGENIAC要件確認を完了。
4. 同一テストセットによる候補比較と安全性確認を完了。
5. 現場の端末・費用・運用体制で継続可能と判断。

モデル、量子化版、プロンプト、利用データ、業務が変わった場合は再評価します。
